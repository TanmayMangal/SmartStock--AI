
# SmartStock AI: AI-Powered Inventory Management and Demand Forecasting

Full-stack inventory system (products, sales, suppliers, purchases, alerts) with a machine-learning
demand forecaster. Everything runs locally and uses free tools.

> **Data notice:** the demo dataset is **synthetic** (generated by `ml-service/generate_data.py`).
> It is not a record of any real business. Rows loaded from it are flagged `is_synthetic = 1` and shown with a
> "demo" tag in the UI. Replace `ml-service/data/*.csv` with real exports (same columns) to use real data.

## Architecture

```
Browser (HTML/CSS/JS + Chart.js)
        |  REST + JWT
Express API  (backend/, port 3000)  ----  MySQL (smartstock)
        |  HTTP (history in, forecast out)
Flask ML service (ml-service/, port 5001)  -- pandas / NumPy / scikit-learn
```

Express also serves the frontend, so you only open http://localhost:3000.

## Setup (Windows/macOS/Linux)

Prerequisites: Node.js 18+, Python 3.10+, MySQL 8.

1. **Database**: open `database/schema.sql` in MySQL Workbench and run it (or `mysql -u root -p < database/schema.sql`).
2. **ML service**
   ```bash
   cd ml-service
   pip install -r requirements.txt
   python generate_data.py      # creates the synthetic CSVs
   python train_models.py       # compares models, writes results/ (tables + PNG charts)
   python app.py                # starts Flask on :5001  (keep running)
   ```
3. **Backend**
   ```bash
   cd backend
   copy .env.example .env       # (cp on macOS/Linux) then edit DB_PASSWORD and JWT_SECRET
   npm install
   npm run seed                 # loads the synthetic demo data into MySQL
   npm start                    # http://localhost:3000
   ```
4. Open http://localhost:3000 and **register**. The first account becomes `admin` (can delete products/suppliers); later accounts are `staff`.

## Modules

| Module | Where | What it does |
|---|---|---|
| Authentication | `routes/auth.js`, `middleware/auth.js` | bcrypt password hashing, JWT (8 h), admin/staff roles, logout |
| Inventory | `routes/products.js` | add / edit / delete, search, category + stock-level filters, manual adjustments |
| Sales | `routes/sales.js` | transactional sale (checks stock, deducts, logs movement); daily/weekly/monthly summaries |
| Suppliers + purchases | `routes/suppliers.js`, `purchases.js` | supplier CRUD, purchase history, purchases add stock automatically |
| Alerts | `routes/alerts.js`, `routes/forecast.js` | low / out-of-stock, stock-movement log, ML-predicted stockouts |
| Forecasting | `ml-service/` | see below |

Sales and purchases use database transactions with `SELECT ... FOR UPDATE`, so stock can never go negative
and every change appears in `stock_movements`.

## Machine learning

**Features** (`features.py`): day of week, month, previous-day sales (lag 1), lag 7, previous 7-day mean,
previous 30-day mean, and trend (7-day mean minus 30-day mean).

**No future leakage:** every lag and rolling feature is built from `qty.shift(1)`, so the value for day *t* only uses days up to *t-1*.
Forecasts for several days ahead are recursive: each predicted day is fed back as history for the next.

**Evaluation** (`train_models.py`): per product, a chronological split (first 80% of days train, last 20% test, no shuffling).
The models are (1) 7-day Moving Average baseline, (2) Linear Regression, (3) Random Forest. Metrics: MAE and RMSE
for one-step-ahead predictions.

**Result on the synthetic data** (average over 12 products, lower is better):

| Model | MAE | RMSE |
|---|---|---|
| Random Forest | 3.452 | 4.326 |
| Linear Regression | 3.455 | 4.359 |
| Moving Average (7d) | 4.105 | 5.125 |

Both ML models beat the baseline by roughly 15%, but Random Forest and Linear Regression are almost tied
(each was best on 6 of 12 products). On this synthetic data the demand patterns are fairly smooth, so the
extra flexibility of a forest buys little. Report that honestly in your viva: the difference is small, and
real, messier data may separate them more. Also note that much of the remaining error is Poisson noise,
which no model can remove.

**Reorder suggestion** (heuristic, `app.py`): forecast demand over the horizon + safety stock
(1.65 x hold-out RMSE x sqrt(lead time), about a 95% service level) minus current stock.

## ML service endpoints

- `GET /health`, `GET /metrics` (saved model comparison)
- `POST /forecast` with `{product_id, history:[{date, qty}], horizon, current_stock, lead_time_days}`

## Testing with Postman

All `/api/*` routes except `/api/auth/*` need the header `Authorization: Bearer <token>` (token from `/api/auth/login`).
Try: `GET /api/products`, `POST /api/sales {"product_id":1,"quantity":2}`, `GET /api/forecast/1?days=14`.

## Known limitations / ideas to extend

- Tested here: data generation, model comparison, the Flask forecast endpoint, and syntax checks of all Node and
  frontend code. The Express routes and UI have **not** been run against a live MySQL in the build environment
  (no database or npm access there), so expect to fix small issues on your first run.
- JWT is stored in `localStorage` (simple, but exposed to XSS; the UI escapes all user text). Production would use httpOnly cookies and HTTPS.
- The forecast model is retrained (and cached) per product on request; for many products, train offline on a schedule.
- No external factors (holidays, promotions, price changes) are used.
- Chart.js loads from a CDN; download it into `frontend/` for fully offline use.
- Ideas: ARIMA/Prophet comparison, prediction intervals, CSV import/export, barcode scanning, PDF reports.
